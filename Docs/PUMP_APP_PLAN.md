# PawnPro Pump — SQL Anywhere 16 → Firebird 5 (PumpAsaFb50)

Status: **active — connections stubbed, pump logic TBD**
Last updated: 2026-04-24
Companion to: [MIGRATION_PLAN.md](MIGRATION_PLAN.md)

This doc is the plan for the **standalone pump app** only. The broader app-migration strategy lives in `MIGRATION_PLAN.md`. If you are picking this up cold, read that first, then this.

---

## 1. Scope

A Delphi VCL utility (`Pump_ASA_FB\PumpAsaFb50.dproj`) that reads a single customer's SAP SQL Anywhere 16 PawnPro database and writes every row into a pre-created Firebird 5 PawnPro database. Run once per store at cutover time.

Not in scope: creating the FB5 database (assume the DBA already ran the 4 DDL scripts in §3), migrating app code (that's Phase 1+ of `MIGRATION_PLAN.md`), live/incremental sync.

---

## 2. Key decisions (deviations from MIGRATION_PLAN.md)

| Area | Pump-app decision | Reason |
|---|---|---|
| ASA source data access | **ADO (`SAOLEDB.12` via `TADOConnection` / `TADOQuery`)** | Delphi **Professional** license does **not** include the FireDAC SQL Anywhere driver (Enterprise-only). ADO is what the main app already uses against ASA, so the connection string is proven. |
| FB target data access | **FireDAC (`TFDConnection` / `TFDQuery`)** | FireDAC Firebird driver ships with Professional. Matches the eventual main-app data layer. |
| Pump engine | **Manual per-table procedures** iterating a TADOQuery on the source and inserting via a parameterized `TFDQuery` on the target | `TFDBatchMove` is the usual fast path, but with ADO on the source side we would need `TFDBatchMoveDataSetReader` wrapping a `TADOQuery` and `TFDBatchMoveSQLWriter` on the target. Can be added later if speed is a problem; manual loop is simpler to debug and gives per-row error reporting in `MemoErrors`. |
| Table-name mapping | Hard-coded per table inside each pump procedure | Only ~23 tables; a metadata-driven mapper is over-engineering for a one-off tool. |
| Key strategy | **Preserve ASA primary keys verbatim**, then reseed FB `TABLE_KEYS` and IDENTITY generators as a post-step | Simplest correctness story — avoids building a translation map for every FK relationship. Assumes the FB DB is **empty** when the pump runs. |
| Re-runnability | **Pump wipes the FB side first** on every run, in reverse-FK delete order, inside one transaction | Pump will be run repeatedly (dry-runs, retries, staging). Wiping via `DELETE FROM` preserves schema/triggers/procs (no DDL re-run). With `GENERATED BY DEFAULT`, explicit-PK inserts do not advance the FB sequence, so pre-pump identity reset is not required — but post-pump reseed in §7 still runs. |
| Image data | Transfer `ImagesData.ImageData` blob bytes via parameterized insert; rely on FireDAC blob streaming. If the source store uses `FILE` mode, pump only the `ImagesData` row (paths) — physical file copy is out of scope for the pump app. | Matches the two `ImageStorageMode` paths already in PawnPro. |

## 3. Pre-conditions

Before running the pump against a store:

1. **ASA server** running with the source database accessible (read-only credentials are fine).
2. **Firebird 5 server** reachable from the pump workstation.
3. **Empty FB5 database file** created, and the DDL applied in this order:
   1. `PawnPro_DB_Firebird50_Schema.sql` — base schema (23 tables)
   2. `PawnPro_FB5_AddMissingObjects.sql` — `INVENTORY_ITEM_STATUS_LOG` + missing FK/indexes
   3. `PawnPro_FB5_FixSchemaDrift.sql` — `TRANSACTION_TYPES` rebuild + `GOLD_PRICE_HISTORY` defaults
   4. `PawnPro_FB5_AddTriggerAndProcs.sql` — trigger, function, stored procs
4. `SAOLEDB.12` provider registered on the workstation running the pump.
5. `fbclient.dll` (matching FB server bitness) on the path, or next to `PumpAsaFb50.exe`.

**The FB5 DB must be empty** — the pump preserves ASA keys, so pre-existing rows would collide.

## 4. Architecture of the pump app

Single form (`TfrmPumpAsaFb50Main`) with:

- **`pnConnections` panel** — editable connection parameters for both sides. Edits: `edAsaServerIP`, `edAsaDBName`, `edAsaUser`, `edAsaPassword`, `edFBServer`, `edFBDBName`, `edFBUser`, `edFBPassword`, `edFBPort`, `edFBCharSet`.
- **`ConnDB: TADOConnection`** — SA source, configured by `GetADOConnectionStr` from the edits.
- **`ConnectionFB: TFDConnection`** — FB target, configured by `ConfigureFBDatabaseConnection` from the edits.
- **`lblCurrentProcess`** — updated as each table pumps.
- **`MemoErrors: TMemo`** — running log (per-table row counts, errors, validation summary).
- **`btnGo`** — triggers the whole pump sequence.

Both config procedures are called at `FormCreate` and should also be re-callable from a "Reconnect" button before pressing **Start Pump**, in case the user edits the fields.

### Column transforms

- Same TitleCase → SNAKE_CASE rule. `Custno` → `CUST_NO`, `TranPawnAmount` → `TRAN_PAWN_AMOUNT`, `InsterestBalance` → `INTEREST_BALANCE` (the ASA typo was corrected in FB), `StationGUID` → `STATION_GUID`.
- One rename that does **not** follow the mechanical rule: ASA `Payments.InsterestBalance` (sic) → FB `PAYMENTS.INTEREST_BALANCE` (typo fixed). Same for `Transactions.InsterestBalance` → `TRANSACTIONS.INTEREST_BALANCE`.
- `InventoryItems.Description` is `VARCHAR(40)` in ASA but `VARCHAR(120)` in FB — widened, no action needed beyond trust the insert.
- ASA `Transactions.TranDate` is `TIMESTAMP`, FB `TRANSACTIONS.TRAN_DATE` is `DATE`. Cast with `CAST(TranDate AS DATE)` on the source query or let ADO → FireDAC narrow it (verify).

### Type transforms (for any generated SQL)

| ASA type | FB5 type | Notes |
|---|---|---|
| `long varchar` | `BLOB SUB_TYPE 1` (text blob) | `CustComment`, `TranComment`, `PayComment`, `ExportLine`, `APIResponse` |
| `image` | `BLOB SUB_TYPE 0` (binary) | `ImagesData.ImageData` |
| `money` | `DECIMAL(18,2)` | `UnitCost`, `UnitPrice` |
| `bit` | `BOOLEAN` | `FTPpassive`, `AutoBackupWhenCloseApp` — ADO returns 0/1; FireDAC param bind as Boolean |
| `datetime` | `TIMESTAMP` | Most `Created` / `ConnStart` / `BckDate` |
| `timestamp` (ASA `TranDate`) | `DATE` in FB | Narrowing — see note above |
| `unsigned int` / `unsigned bigint` | `INTEGER` / `BIGINT` | FB has no unsigned; values in this schema fit signed range |

## 5a. FB wipe order (reverse-FK)

Run as the first step of every pump. All 29 tables in the reverse of the §6 pump order, i.e. children before parents:

```
PAYMENTS, STONES, SALES_ITEMS, INVENTORY_ITEM_STATUS_LOG,
IMAGES_DATA_BACKUP, IMAGES_DATA, INVENTORY_ITEMS, TRANSACTIONS,
CUSTOMER, EXPORT_LOG_FILE_DETAIL, EXPORT_FILE_LOG,
GOLD_PRICE_HISTORY, BACKUP_HISTORY, TABLE_KEYS,
INV_CATEGORIES, IMAGES_TYPES, PAYMENT_TYPES, TRANSACTION_TYPES,
ITEM_STATUS, J_STONE_COLORS, J_STONE_SHAPES, J_GENDERS,
J_STYLES, J_METALS, J_TYPES, EXPORT_FORMAT,
BACKUP_SETTINGS, STORE, STATES
```

Each is an unqualified `DELETE FROM <tbl>`. One FB transaction wraps the whole wipe; commit on success, roll back on any error (nothing pumped yet — safe to abort the run).

## 6. Pump order (FK-safe)

Parents before children. Reference/lookup tables first since they have no FKs and populate the domains used by the data tables.

```
1.  States                        10. JStoneColors
2.  Store                         11. ItemStatus
3.  BackupSettings                12. TransactionTypes
4.  ExportFormat                  13. PaymentTypes
5.  JTypes                        14. ImagesTypes
6.  JMetals                       15. InvCategories
7.  JStyles                       16. TableKeys       (copy rows; reseeded in post-step)
8.  JGenders                      -------- data ----------
9.  JStoneShapes                  17. Customer
10. JGenders                      20. Transactions         (FK → Customer)
11. JStoneShapes                  21. InventoryItems       (FK → Transactions)
                                  22. Stones               (FK → InventoryItems)
                                  23. SalesItems           (FK → InventoryItems, by convention)
                                  24. Payments             (FK → Transactions)
                                  25. ImagesData           (logical FK to many tables via ImagRefToRowNo)
                                  26. ImagesDataBackup
                                  27. InventoryItemStatusLog
                                  28. BackupHistory
                                  29. ExportFileLog
                                  30. ExportLogFileDetail
                                  31. GoldPriceHistory
```

(Within a single load the per-row inserts will commit; consider wrapping each table in an FB transaction for atomicity and to allow rollback on failure.)

## 7. Post-pump steps

Run these after all row-by-row work completes, before handing the DB to the customer:

1. **Reseed IDENTITY generators** for every table that has `GENERATED BY DEFAULT AS IDENTITY`. For each such table:
   ```sql
   ALTER TABLE <tbl> ALTER COLUMN <pk> RESTART WITH <MAX(pk)+1>;
   ```
   Tables affected: `CUSTOMER`, `PAYMENTS`, `INV_CATEGORIES`, `SALES_ITEMS`, `STONES`, `BACKUP_HISTORY`, `EXPORT_FORMAT`, `EXPORT_FILE_LOG`, `EXPORT_LOG_FILE_DETAIL`, `IMAGES_TYPES`, `IMAGES_DATA`, `INVENTORY_ITEM_STATUS_LOG`, `GOLD_PRICE_HISTORY`.
2. **Verify `TABLE_KEYS`** values are `≥ MAX(pk)` of their referenced table — specifically `Transactions` and `InventoryItems` whose keys are app-managed via `fn_GetNextKey`. If a row was copied but the `TABLE_KEYS` row was stale, bump it.
3. **Validation pass** — write to `MemoErrors`:
   - Row count per table, ASA vs. FB.
   - `SUM(TranPawnAmount)` / `SUM(PayAmount)` parity.
   - `MAX(PayDate)`, `MAX(TranDate)` parity.
   - Image count parity per `ImageTypeNo`.
4. **Write a log file** next to the EXE: `PumpAsaFb50.<yyyymmdd-hhmmss>.log` with everything that was in `MemoErrors`, for the store's audit trail.

## 9. Open questions / decisions needed

1. **Which driver bitness** for `fbclient.dll`? App is Win32/Win64 per `MIGRATION_PLAN.md` — confirm which the pump ships as. (Currently unknown; `.dproj.local` suggests Win64 was built last.)
2. **`TFDBatchMove` later?** If a large store (say >200k inventory rows) pumps too slowly with the row-by-row approach, switch the high-volume tables (`INVENTORY_ITEMS`, `PAYMENTS`, `INVENTORY_ITEM_STATUS_LOG`, `IMAGES_DATA`) to `TFDBatchMove` with an ADO-dataset reader.
3. **Character set.** ASA collation is `1252LATIN1`; FB DB is being defined with `UTF8` columns on `CUSTOMER`. FireDAC `CharacterSet=UTF8` on the target + ADO driver on the source will convert. Spot-check a customer with accented characters after the first real pump.
4. **Deprecated columns to skip on pump.** The following ASA columns do not exist on the FB side and must be omitted from the pump's `SELECT`/`INSERT` lists:
   - `Customer.StationID`, `Customer.StationSEQ` — retired multi-station-sync feature.
   - `Customer.CustTicketNo` — legacy denormalized ticket number; now lives on `Transactions.TranTicketNo`. Main ASA app still references the field (`PawnDM.pas:67` `qryCustomersCustTicketNo`); those references will be removed from the main app as part of the FB cutover.
