# Declaring a day with no pawns

Design note. Written 2026-11-16, not yet built.

Gema Jewelers' local police want to be told when a day had no pawn activity,
rather than inferring it from silence. Today that means someone logging into the
LeadsOnline website by hand. The web service can do it directly, so PawnPro can
offer a button and the store never leaves the application.

## What this is, before anything else

**It is a statement to law enforcement that nothing happened.** Not a UI
convenience with a network call attached. Every rule below follows from that, and
where convenience and truthfulness disagree, truthfulness wins — a missing
declaration is a gap someone can notice and chase, while a false one is a lie
nobody will ever question.

## The API already supports it

`SetNoTransactionDayForStore`, one of the eight operations on `ticketWS`, and
already present in the generated `LeadsOnlineWS.pas`:

```pascal
function SetNoTransactionDayForStore(const ApiVersion: Integer; const IpAddress: string;
                                     const TransactionDate: string; const login: LoginInfo): Response;
```

A date and the login. It returns the same `Response` with an `errorCode` as
every other call, so `LeadsOnlineErrorText` already knows how to describe the
outcome.

Nothing about the transport, credentials, TLS pinning or error decoding needs to
change. This is a fourth operation alongside the three we already wrap.

## What has to be built

### 1. Client wrapper — `uLeadsOnlineClient`

Two methods, following the existing shape exactly:

```pascal
function SetNoTransactionDay(ADate: TDate): TLeadsOnlineResult;
function TrySetNoTransactionDay(ADate: TDate; out AResult: TLeadsOnlineResult;
                                out AError: string): Boolean;
```

`Try*` returns **True when the service was reached**, with `AResult` carrying
what it said — the same contract as `TrySubmitTransaction` and `TryUploadImage`.
"Reached and refused" and "never reached" are different problems and must stay
distinguishable, which is the whole reason that convention exists.

### 2. A record of what was declared

A new table. The reason is the same one `LEADS_SOAP_SUBMISSION` exists for: six
months on, "did we tell them about the 14th?" must be answerable from the
database, not from memory.

```sql
CREATE TABLE LEADS_SOAP_NO_ACTIVITY
(
  ID                INTEGER   GENERATED BY DEFAULT AS IDENTITY (START WITH 1) NOT NULL,
  ACTIVITY_DATE     DATE      NOT NULL,
  DECLARED_AT       TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL,
  ERROR_CODE        INTEGER,
  ERROR_RESPONSE    VARCHAR(500),
  CONSTRAINT PK_LEADS_SOAP_NO_ACTIVITY PRIMARY KEY (ID),
  CONSTRAINT UQ_LEADS_SOAP_NO_ACTIVITY UNIQUE (ACTIVITY_DATE)
);
```

`UNIQUE (ACTIVITY_DATE)` stops the same day being declared twice.

**This is a schema change, so it needs all four steps** from CLAUDE.md —
migration script, `Schema.sql`, regenerate the full-deploy, and a `Step<N>_*` in
`uDBMigrations` with `CURRENT_DB_VERSION` bumped. Step (4) is the one that
matters: the USB template is deliberately stale, so the migration runner is the
only thing that will put this table in front of a store.

### 3. A button, on the LeadsOnline export screen

Beside the existing controls. It opens a small dialog: pick the date, see what
the check below found, confirm.

## The rules, and why each exists

### Default to yesterday, and never allow the future

You cannot truthfully say "no pawns today" at two in the afternoon. Default the
date to **yesterday**, allow the operator to pick an earlier one, and refuse a
date later than yesterday outright.

### Refuse when the day was not actually empty

The application knows whether that date had transactions. If it did, **do not
send** — explain what was found instead. A clerk clicking through a confirmation
they half-read must not be able to file a false statement.

This must be in the code, not in the training.

### What "empty" means is wider than the TRANSACTIONS table

Check three things for that date, not one:

| | why |
|---|---|
| `TRANSACTIONS` | the obvious one |
| `LEADS_SOAP_SUBMISSION` | a ticket already reported for that date proves the day was not empty, even if the transaction has since gone |
| `EXPORT_LOG_FILE_DETAIL` | the same for the older CSV channel |

**The second and third are there because of Gema**, who asked for this feature.
They delete pawns once redeemed or defaulted — 86% of their history is gone, and
transaction 3457 was found reused under a new ticket number. A day that looks
empty in their `TRANSACTIONS` table is not evidence the day *was* empty. The
submission log is the more trustworthy witness, because it records what was sent
rather than what still exists.

A store that deletes its history is exactly the store most likely to produce a
false "no activity" day, and the only one who has asked for the feature.

### Manual, not automatic — for now

An unattended job that declares no-activity every night is the obvious next
thought. Resist it until this has been in use for a while.

A **missed** declaration is visible: the police notice nothing arrived and ask.
A **wrong automatic** declaration is invisible: it is filed, it is believed, and
nobody looks again. The failure modes are not symmetrical, and the automatic one
is on the wrong side.

Revisit once there is evidence of how often it is used and whether the checks
above ever actually fire.

### Say what happened, in the same words as everything else

Reuse `LeadsOnlineErrorText`. Reuse the Sent / Failed vocabulary from the export
screen. An operator should not have to learn a second set of words for the same
service.

## Showing it afterwards

`View Sent Tickets` answers "did last week go out?" and a declared no-activity
day belongs in that answer. Simplest version: a row in the same grid with the
date, "No activity declared" in the Result column, and no ticket number.

Worth doing at the same time. A declaration nobody can see afterwards is only
half the feature — the store's reason for wanting this is to be able to show the
police they complied.

## Open questions for the store

1. **Does it have to be every empty day, or only when asked?** Changes whether
   this is a once-a-week habit or a daily one.
2. **Which days count?** A shop closed on Sunday has no pawns every Sunday.
   Whether the police want those declared, or only days the shop was open and
   quiet, is their question, not ours.
3. **Is this Gema's local department only, or Florida-wide?** Determines whether
   the button is visible everywhere or behind a per-store setting.

Question 2 matters most. If closed days count, the store will want a way to
declare several at once, and that is a different screen.
